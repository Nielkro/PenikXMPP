# План: разбор и фиксы FunXMPP (`server/mod_funxmpp.lua` + `xmpp/fun/`)

## Контекст

Внешний разбор модуля заявил 5 проблем: отвал `mod_smacks` на `<r/>`/`<a/>`,
разрушение порядка детей в `CONTENT_MIXED`, утечка памяти на конкатенации
`session.funxmpp_in_buf`, неконсистентность длин `0xFFFF`, оверхед поиска `@` в JID.
Проверка по исходникам Prosody (`mod_c2s.lua`, `core/stanza_router.lua`,
`util/filters.lua`, `util/stanza.lua`, `mod_smacks.lua`) и по коду клиента
(`FunWriter.java`, `FunReader.java`, `Element.java`, `TagWriter.java`, `XmlReader.java`)
показала: из пяти пунктов реален один (частично), один — реален, но некритичен,
три — мимо. Плюс найден один настоящий критический баг, который разбор пропустил
(исходящий piggyback `<r/>` от smacks рвёт бинарный фрейминг).

Ниже: что чиним, почему, как проверяем. Что не чиним — с причинами.

## Фикс P0 (критично): исходящий piggyback `<r/>` от `mod_smacks` проходит мимо бинаризации

### Что

`mod_smacks.lua:outgoing_stanza_filter` (приоритет `-1000` на `stanzas/out`) при
`#queue > max_unacked_stanzas and not session.awaiting_ack` (дефолт
`smacks_max_unacked_stanzas = 0`, то есть почти на каждой станзе) возвращает
**строку**: `tostring(stanza) .. tostring(<r/>)`.

Наш `funxmpp_stanzas_out` (`server/mod_funxmpp.lua:523-538`, приоритет `-10000`,
идёт позже — в `util/filters.lua` higher-first, тут порядок верный) получает уже
строку, проверка `type(stanza) ~= "table"` пропускает её как есть. В бинарный
поток уезжает сырой XML. Клиентский `FunReader.readElement` прочитает `<`
(`0x3C`) как старший байт длины фрейма — рассинхрон потока, обрыв сессии.

### Почему именно так

- Порядок фильтров верный (`-1000` раньше `-10000`), smacks видит XML-объект —
  это правильно, ломать не надо.
- Переносить funxmpp-фильтр раньше smacks нельзя: `st.clone` в smacks упадёт на
  wrapper-таблице (`clone` требует метатаблицу `stanza_mt`, а `ipairs` не видит
  детей через `__index`).
- Отдельный `<r/>` через `session.send` (например из `handle_read_timeout`)
  идёт через энкодер нормально — проблема только в строковой склейке.

### Как исправить (рекомендуемый вариант, без XML-парсинга на горячем пути)

1. В `server/mod_funxmpp.lua` добавить лёгкий `stanzas/out`-фильтр с приоритетом
   `-999` (сразу выше smacks): если вход — таблица-станза, сохранить её в
   `session.funxmpp_last_out` и вернуть без изменений.
2. В `funxmpp_stanzas_out` (`-10000`) обработать строковый вход: если вход —
   строка, `session.funxmpp_last_out` выставлен и строка оканчивается паттерном
   `<r xmlns=["']urn:xmpp:sm:[23]["']/>`, вернуть **два бинарных фрейма**:
   `encode_stanza(stashed)` + `encode_stanza(r_node)` вместо сырого XML.
   После обработки `session.funxmpp_last_out` сбрасывать.
3. Строки stream-уровня (`<stream:stream>`, `</stream:stream>`, `stream:error`
   из `session_close`) не трогать — они не станзы и идут мимо бинаря осознанно;
   условие по суффиксу `<r .../>` их отсекает.
4. Запасной вариант (если склейка окажется шире одного кейса): конфиг
   `smacks_max_unacked_stanzas` большим значением на время funxmpp-сессий,
   ack-запросы тогда только через `c2s-read-timeout` отдельными станзами.
   Минус — меняется поведение и для XML-клиентов, поэтому основной путь —
   пункт 2.

### Проверка

- Юнит: прогнать через пару фильтров станзу при `awaiting_ack == nil`,
  убедиться, что на выходе два валидных length-префиксных фрейма, а не XML.
- Интеграция: реальный Prosody + `mod_smacks` + клиент, в логе сокета после
  `funxmpp_enabled` не должно быть байта `<` вне XML-хендшейка.
- Регресс: ack-цикл (`<r/>` → `<a h/>`), очередь smacks чистится
  (`#queue` падает), resume переотправляет очередь.

## Фикс P1 (реальный, низкий приоритет): `CONTENT_MIXED` теряет порядок детей

### Что

Энкодер (`server/mod_funxmpp.lua:315-337`, `FunWriter.java:62-76`) склеивает весь
текст в начало, детей — в конец. `текст-ребёнок-текст` превращается в
`тексттекст-ребёнок`. Декодер читает в том же неверном порядке.

### Почему низкий приоритет

- Пример из разбора (`<body>` с `<b>` внутри) — невалидный XMPP: `<body>`
  по RFC только текст.
- Единственный реальный mixed — XHTML-IM, который современные серверы режут,
  а клиентский `Element.java:40-63` вообще не представляет: `addChild` зануляет
  `content`, `setContent` чистит `children`. Исходящий mixed клиент создать не
  может; входящий `FunReader.java:81-83` ещё и теряет текст (`setContent`, затем
  `addChild` сбрасывает его в `null`).

### Как исправить (когда понадобится, breaking change)

1. Формат v2: вместо `текст + дети` — flat-sequence с маркером типа ноды
   (`0x01` текст-чанк / `0x02` дочерний элемент) в естественном порядке обхода.
2. Поднять `version` в stream-features и словарь (`DICTIONARY_HASH`), сервер
   принимает v1 и v2 на переходный период.
3. На клиенте сначала расширить `Element` (сосуществование `content` +
   `children` без взаимного сброса), затем `FunWriter`/`FunReader`, затем
   `XmlReader` (mixed-путь `Tag.No` сейчас отбрасывает текст при непустых детях:
   `XmlReader.java:166-170`).
4. До этого — зафиксировать поведение v1 как «mixed не поддерживается»
   (документировать, а не молча переупорядочивать).

### Проверка

- Round-trip `Lua → Lua`, `Java → Java`, `Lua ↔ Java` на XHTML-IM станзе с
  перемежающимся текстом; порядок нод байт-в-байт.
- Старые клиенты v1 против нового сервера и наоборот (негоциация версии).

## Улучшения P2 (не баги, делать по желанию)

### P2.1. Входной буфер без `..`/`sub` на каждый чанок

`session.funxmpp_in_buf = (... or "") .. data` + `:sub(...)`
(`server/mod_funxmpp.lua:469,496`) — не утечка (GC подбирает), а churn.
При желании: таблица чанков + суммарная длина, либо `buf_offset` с подрезкой
`sub` только когда offset перевалил порог (например 64 КБ). Эффект заметен лишь
на тысячах коннектов с фрагментацией по 100–200 Б; TCP обычно коалесцирует.

### P2.2. Унификация длин — только в доку, код не трогать

`FA/FB/FC` (ширина литерала) и `0xFFFF`-sentinel + `u32` (фрейм/тело/текст) —
два слоя, обе стороны (`mod_funxmpp.lua` ↔ `FunWriter/FunReader.java`)
симметричны, грань `len == 0xFFFF` везде уходит в расширенную форму корректно.
Клиент не «споткнётся». Можно описать оба слоя в одном месте спеки.

### P2.3. Мелочи исходящего фильтра

- Счётчики `funxmpp_stats` внутри `__tostring` double-count при повторном
  `tostring` (логирование + отправка). Считать на уровне фильтра, а не в
  `__tostring`.
- Счётчик атрибутов — один байт (`string.char(#attr_list)`); >255 атрибутов
  нереалистично, но стоит явный assert вместо молчаливого усечения (то же в
  `FunWriter.java:50`).
- Неизвестный токен декодер превращает в строку `"unknown_0x.."` и молча портит
  станзу — лучше дропать фрейм с логом.

## Не чиним (сверено с исходниками, причины)

### Входящие `<r/>`/`<a/>` через `core_process_stanza` — работает как есть

Разбор утверждает, что роутер их проигнорирует. На деле
`core/stanza_router.lua:core_process_stanza` при `xmlns ~= nil` фаерит
`stanza/urn:xmpp:sm:3:r` (и `:a`), на которых висит `mod_smacks` через
`hook_stanza`. `decode_node` (`mod_funxmpp.lua:403-408`) `xmlns="urn:xmpp:sm:3"`
сохраняет, входящий `session.filter("stanzas/in", ...)` даёт smacks посчитать
станзу (`count_incoming_stanzas`, приоритет `1000`). Предложенный в разборе
`(session.process_smacks or session.fire_event)("smacks/stanza", ...)` —
несуществующий API; вставлять его нельзя, это сломает SM. Отдельный нюанс:
вызов идёт синхронно из `bytes/in`-фильтра в обход `session.thread`-раннера
`mod_c2s` — порядок на одном коннекте сохраняется, но долгие обработчики будут
держать чтение сокета; выносить в раннер — только если проявятся stalls.

### Поиск `@` в JID-токенизации — не просадка

`str:find("@", 1, true)` / `indexOf('@')` — плоский `memchr` на строках в
единицы-десятки байт. Ограничение «только `to/from/jid/by`» хрупко (доменные
токены живут и в других атрибутах), generic-путь проще и безопаснее.

## Порядок работ и риски

1. P0 (один коммит, scope `server`): stash-фильтр `-999` + строковая ветка
   `-10000` + юнит/интеграция по разделу «Проверка».
2. P1 (отдельно, только если нужен XHTML-IM): формат v2 + негоциация версии +
   `Element`-модель; ломающее изменение, катить флагом/версией.
3. P2 по желанию, каждый пункт отдельным коммитом.
4. Не трогать: входящий SM-путь, JID-`find`, ширину строк — verified as-is.

Основной риск — P0: фильтр затрагивает каждую исходящую станзу smacks-сессий,
тестировать ack/resume именно под нагрузкой (дефолтный `max_unacked = 0`
даёт piggyback почти на каждой станзе — это и есть триггер бага).

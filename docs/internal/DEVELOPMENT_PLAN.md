## Timeline (Recent Releases)

### Unreleased: per-group archive history
- Personal group settings store automatic mode or a 1–365-day period for each account/room. An explicit load action reuses the serialized MAM queue without sending join/leave presence.
- Chat menus and Ctrl+Shift+H request history for the selected group or direct contact. Direct-contact queries use the account archive with a peer filter and keep account-wide catch-up coverage unchanged.
- Custom periods override the normal history window while preserving panic-wipe, cleared-history and expiry boundaries. Existing profiles default to automatic mode.
- MAM catch-up corrects filtered-completion coverage and new-visit cursor handling; the schema migration rebuilds coverage metadata while retaining messages, keys and account settings.

### v2.0.0 release baseline (File-transfer pipeline durability)
- **Restart-safe transfer state**: stale persisted `IN_PROGRESS` file-transfer rows are normalized to `FAILED` at startup; completed local files remain available, interrupted Jingle live sessions are not falsely byte-resumed
- **Outgoing retry**: failed sent transfers with a persisted encrypted local copy can retry upload from that copy without the original source file; the default file UI exposes "Retry upload"
- **Large-file gates**: outgoing local-save and received store paths are covered with >1 MiB deterministic streams and bounded 8192-byte read chunks
- **Server persistence lookup**: 1:1 MAM/server-id replay can match resourceful stored messages from a bare conversation; XEP-0198 ack waiting remains out of scope
- **Scope**: encrypted Tor-onion variants stay behind this durable baseline, and a product v2-only OMEMO2/JET receiver mode is not a current production-release blocker

## Forward-Looking Roadmap

### May 2026: Encrypted File Transfer Pipeline

This section reconciles the archived May 17 audit and TODO notes with the current branch. The archived notes remain the design evidence; this table is the current live plan. Do not restart this effort from a fresh design unless these checkpoints are first re-audited against the current code.

The pipeline goal is broader than encrypted-transfer safety. DinoX needs stable file transfers that keep the chat UI responsive while upload, download, encryption, decryption, hashing, signature verification, storage, preview preparation and cleanup run outside the UI flow. The target architecture is a dedicated transfer worker/job boundary with cancellation, progress, failure reporting and cleanup, while the UI only observes phase/state transitions and final verified results.

The runtime matrix has four file-transfer security scenarios: unencrypted, OMEMO, XEP-0027 legacy OpenPGP, and XEP-0373/XEP-0374 OpenPGP for XMPP. Audio/video calls are out of scope because they use the RTP/WebRTC/Jingle media stack. Audio and video messages are in scope because they are recorded, sent, received, decrypted, verified, stored and played back as files.

OpenPGP is part of this pipeline. The current OpenPGP integration is functional and ready for the pipeline work, but it is not the sole foundation of the pipeline and it does not prove the complete file-transfer pipeline is finished. OpenPGP remains a separate test and regression surface because edge-case failures can still appear during pipeline work. OpenPGP file transfer uses HTTP/SFS with the body URL protected inside the OpenPGP-encrypted message body; it is not an encrypted Jingle/JET transport variant.

Before the next implementation slice, the accumulated pipeline work must pass through an explicit **Integration Gates / Matrix Proof** checkpoint. This is not a new architecture restart; it is the proof layer for the work already done. `docs/internal/FILE_TRANSFER_PIPELINE_TODO.md` owns the detailed gate plan and run log. New code should not continue past this checkpoint unless the current focused suites are re-run, the missing runtime combinations are recorded, and any regression found by the gates is fixed or promoted to a blocking TODO.

### Q2 2026: PipeWire Compatibility (Video Messages & Call Pipeline)

| Item | Description | Status |

| **Video Messages: pipewiresrc → autovideosrc** | Replace direct `pipewiresrc` usage in `video_recorder.vala` with `autovideosrc`. Fixes EINVAL (-22) on PipeWire >= 1.2 (openSUSE, Fedora, Arch, Ubuntu 26.04 LTS with PipeWire 1.6.0).
